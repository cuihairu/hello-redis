# User message timeline

A timeline is at the core of microblogging and Moments-style applications: after publishing a post, followers should see it on their feed. There are two common write strategies: the push model (write fan-out) and the pull model (read fan-out), and real projects often use a mix.

## Data structure design

- `timeline:{user_id}`: a person's home feed timeline, using a sorted set, with the score storing the post timestamp in milliseconds and the member storing the message ID;
- `posts:{user_id}`: all messages a person has published themselves (with write fan-out, they are also delivered to every follower's timeline).

## Command demo

```bash
# Publish a message (assuming the message ID is generated by an ID generator)
INCR post:id                                    # 1
ZADD posts:42 1717382400000 1

# Push model: write to the author's own timeline and each follower's timeline
ZADD timeline:43 1717382400000 1
ZADD timeline:44 1717382400000 1

# Feed: take the 20 most recent items in reverse chronological order
ZRANGE timeline:43 0 19 REV WITHSCORES

# Pagination: use a message's score as the cursor to fetch earlier content
ZRANGE timeline:43 (1717382400000 -inf BYSCORE REV LIMIT 0 20

# Keep only the most recent 1000 items to prevent unbounded timeline growth
ZREMRANGEBYRANK timeline:43 0 -1001
```

## Python example

```python
import time
import redis

r = redis.Redis(decode_responses=True)
TIMELINE_LEN = 1000


def publish(user_id, content):
    post_id = r.incr('post:id')
    now = int(time.time() * 1000)
    pipe = r.pipeline()
    pipe.zadd(f'posts:{user_id}', {post_id: now})
    # Write fan-out: deliver to the author's timeline and the followers' timelines
    pipe.zadd(f'timeline:{user_id}', {post_id: now})
    for fan in r.sscan_iter(f'fans:{user_id}', count=500):
        pipe.zadd(f'timeline:{fan}', {post_id: now})
    pipe.execute()
    return post_id


def home(user_id, size=20):
    ids = r.zrange(f'timeline:{user_id}', 0, size - 1, desc=True, withscores=True)
    return [(int(pid), score) for pid, score in ids]


def home_before(user_id, cursor_score, size=20):
    return r.zrange(f'timeline:{user_id}', f'({cursor_score}', '-inf',
                    byscore=True, desc=True, offset=0, num=size, withscores=True)


def trim(user_id):
    r.zremrangebyrank(f'timeline:{user_id}', 0, -TIMELINE_LEN - 1)


if __name__ == '__main__':
    r.sadd('fans:42', 43, 44)
    post_id = publish(42, 'hello world')
    print(post_id, home(43))   # The feed can see the message posted by 42
```

## Push model and pull model

- **Push model (write fan-out)**: On publish, write to every follower's timeline. Reads are a single `ZRANGE ... REV` at O(log N), but a power user posting one message means millions of writes. Suits social circles where follower counts are generally small.
- **Pull model (read fan-out)**: Only write to the author's own `posts`; when followers refresh their feed, pull all followed accounts' `posts` and merge-sort them. Reads need `ZUNIONSTORE` or an application-layer merge, and it suits power-user scenarios.
- **Hybrid model**: Regular users push, power users with over a million followers pull; or the timeline only caches the most recent items, with historical content fetched from the source.

## Practical advice

- Keep the timeline as a lightweight "ID + timestamp" index only; put large payloads such as the body in separate keys or a database, and fetch them in batch with `MGET`/pipelines.
- Use `ZREMRANGEBYRANK` to cap the length, and archive historical messages before reading them.
- Pagination must use a timestamp cursor (`ZRANGE ... (score BYSCORE REV`), not a large offset with `ZRANGE ... REV`, to avoid duplicates or skipped reads caused by new messages being inserted.
