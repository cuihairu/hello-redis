# Redis架构与设计

Redis 是一个基于内存的键值数据库，其设计目标是在保证简单可靠的前提下提供亚毫秒级的读写延迟。理解它的整体架构，有助于解释日常运维中遇到的各种现象（如慢查询、阻塞、持久化抖动等）。

## 顶层结构

Redis 服务端可以粗略分为四层：

1. **网络层**：基于 I/O 多路复用（epoll/kqueue/select）的事件驱动模型，负责监听连接、读取请求和回写响应。
2. **协议层**：解析 RESP（REdis Serialization Protocol）协议，把客户端发来的字节流还原成命令与参数。
3. **命令执行层**：通过命令表（Redis 7.0 后为 `redisCommandTable`）查找命令实现函数，完成参数校验、权限检查后执行。
4. **存储层**：由各种数据结构（SDS、字典、跳表、listpack 等）组成的键空间，配合过期、淘汰、持久化、复制等机制。

## 单线程模型

Redis 的命令执行是单线程的：所有客户端命令在一个主线程中串行执行。这带来了两个重要性质：

- **无需加锁**：命令之间天然互斥，`INCR` 等复合操作天然原子。
- **不能有慢操作**：任何一个耗时命令（如对百万成员的键执行 `KEYS`、`SMEMBERS`、`HGETALL`）都会阻塞后续所有请求，这是生产环境禁用 `KEYS`、要求拆分大键的根本原因。

单线程并不等于整个进程只有一个线程。以下工作在其他线程完成：

- **后台线程**：Redis 4.0 起提供 `UNLINK`（异步删除大键）、`BGREWRITEAOF`/`BGSAVE` 的 fsync 刷盘等由后台线程处理。
- **I/O 线程**：Redis 6.0 起支持配置 `io-threads`，让网络读写与协议解析并行执行，命令执行仍在主线程。

## 事件循环

Redis 使用自己实现的事件库（ae.c）封装操作系统 I/O 多路复用，主循环处理两类事件：

- **文件事件（File Event）**：套接字可读/可写，即客户端请求到达、响应可以发送；
- **时间事件（Time Event）**：周期任务，如过期键的主动删除（`activeExpireCycle`）、集群心跳、`replCron` 等。

主循环每轮先处理到期的时间事件，再处理文件事件；事件之间相互独立，任何一个回调耗时过长都会拖慢整体延迟。

## 内存存储与持久化的关系

所有数据都保存在内存中，持久化（RDB/AOF）只是把内存状态异步落盘的机制：

- RDB 通过 `BGSAVE` fork 子进程生成快照，利用写时复制（COW）避免阻塞主线程；
- AOF 在主线程追加写缓冲，由后台线程执行 fsync。

因此持久化配置的取舍，本质上是在"崩溃时可以丢多少数据"与"fork、刷盘带来的延迟毛刺"之间做权衡。

## 与客户端的交互方式

客户端与 Redis 之间是简单的请求-响应协议，同时支持两种批量优化：

- **管道（Pipeline）**：客户端一次发送多条命令，服务端按序回复，节省网络往返（RTT）；
- **事务/脚本**：`MULTI/EXEC` 保证命令的串行执行，Lua 脚本则把多条命令打包成一次往返的单个原子操作。

## 小结

"内存存储 + 单线程命令执行 + 事件驱动 I/O"是 Redis 高性能的三大支柱，也是其使用约束（避免慢命令、避免大键、数据量受内存限制）的根源。相关实现细节可进一步阅读[核心数据结构与算法](core-data-structures.md)与[命令执行与事件处理](command-execution.md)。
