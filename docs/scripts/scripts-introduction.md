# 脚本功能介绍

Redis 的脚本功能把一段程序发送到服务器端执行，在服务器内部一次完成多条命令的操作。它主要解决两个问题：**多次网络往返带来的延迟**与**多步操作之间的并发一致性**。

## 1. 脚本解决什么问题

没有脚本时，一个「读取-判断-写回」的业务动作要拆成多条命令、多次往返：

```bash
GET stock:1001        # 读取库存
# 客户端判断余量
DECR stock:1001       # 扣减库存
```

两个天然缺陷：一是每条命令一次 RTT，逻辑越复杂延迟越高；二是两个客户端可能同时读到相同余量，导致超卖或数据错乱。脚本把这段逻辑整体发送到服务器端执行，执行期间 Redis 不处理其他命令，两个问题一次解决。

## 2. 基本形态

脚本语言是 Lua，通过 `EVAL` 执行：

```bash
EVAL "local n = tonumber(redis.call('GET', KEYS[1])) if n > 0 then return redis.call('DECR', KEYS[1]) end return -1" 1 stock:1001
```

脚本内的三要素：`KEYS` 声明要访问的键名数组，`ARGV` 传键名以外的参数，`redis.call` / `redis.pcall` 在脚本内执行 Redis 命令。

两种脚本形态共用同一个内嵌 Lua 引擎，语法与 API 完全一致：

| 形态 | 命令 | 特点 |
| --- | --- | --- |
| Lua 脚本 | `EVAL` / `EVALSHA` | 即发即执行，配合 `SCRIPT LOAD` 缓存脚本，按 SHA1 复用 |
| Functions（7.0+） | `FUNCTION LOAD` / `FCALL` | 以库为单位命名与管理，随复制与持久化同步，适合长期维护 |

## 3. 核心性质

- **原子性**：脚本执行期间服务器被独占，其他客户端的命令排队等待；并发客户端要么看到脚本执行前的状态，要么看到执行后的状态，不会看到中间状态。「检查再设置」「扣减再判断」这类多步逻辑可以不依赖分布式锁直接实现。
- **读到的是稳定数据**：独占执行期间脚本内读到的数据不会被并发修改，无需额外加锁。
- **出错不回滚**：脚本中途出错时已执行的写命令仍然生效，因此脚本内部要先做参数校验再写入。
- **缓存复用**：脚本执行后被缓存，之后可用 `SCRIPT LOAD` 返回的 SHA1 通过 `EVALSHA` 执行，省去重复传输脚本内容。
- **沙箱受限**：只能使用 Redis 内嵌 Lua 的 `string`、`table`、`math`、`cjson`、`cmsgpack`、`struct`、`bit` 等安全库，不能执行文件、网络与系统调用。

## 4. 与事务（MULTI/EXEC）的取舍

| 需求 | 更适合的机制 |
| --- | --- |
| 顺序执行一批固定命令，不需要中间判断 | `MULTI` / `EXEC` 事务 |
| 需要「读取后根据值决定后续命令」的分支逻辑 | Lua 脚本 |
| 需要在服务器端做计算、聚合、转换 | Lua 脚本 |
| 需要长期维护、随主从同步的脚本集合 | Functions（Redis 7.0+） |

## 5. 使用限制与注意事项

- **键全部走 KEYS 声明**：这是集群路由与安全性的要求，不要只把键名放 ARGV 里传。
- **控制执行时间**：超过 `busy-reply-threshold`（默认 5000 毫秒）后其他客户端会收到 `BUSY` 错误，只能 `SCRIPT KILL`（脚本尚未写过数据时）或 `SHUTDOWN NOSAVE`；避免对大集合做全量遍历。
- **生产环境用 EVALSHA 或 Functions**：常用脚本先 `SCRIPT LOAD` 再 `EVALSHA`，客户端捕获 `NOSCRIPT` 错误后重新加载再重试。脚本内容一改，SHA1 校验和就变，需要重新加载。

## 6. 典型应用场景

- **分布式锁解锁**：用一段脚本完成「判断持有者-删除锁」的原子操作。
- **限流器**：结合 `INCR` 与 `EXPIRE` 实现固定窗口计数。
- **排行榜更新**：一次脚本内更新分数并返回新排名。
- **库存扣减**：读取库存、判断余量、扣减并记录，一步完成。
