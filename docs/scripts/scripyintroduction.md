# 脚本功能介绍

本页介绍 Redis 的脚本功能。主题与《脚本功能介绍》（scripts-introduction.md）一致，可互相参照；本页侧重从"为什么需要脚本"的角度做整体梳理。

## 1. 脚本解决的问题

在没有脚本的情况下，一个业务动作往往要拆成多条命令、多次网络往返：

```bash
GET stock:1001        # 读取库存
# 客户端判断余量
DECR stock:1001       # 扣减库存
```

这种"读取-判断-写回"的模式存在两个天然缺陷：

1. **多次往返**：每条命令一次 RTT，逻辑越复杂延迟越高。
2. **并发不安全**：两个客户端可能同时读到相同的余量，导致超卖或数据错乱。

脚本把这段逻辑整体发送到服务器端执行，服务器在脚本运行期间不处理其他命令，从而一次性解决上述两个问题。

## 2. 脚本的基本形态

Redis 使用的脚本语言是 Lua，通过 `EVAL` 命令执行：

```bash
EVAL "local n = tonumber(redis.call('GET', KEYS[1])) if n > 0 then return redis.call('DECR', KEYS[1]) end return -1" 1 stock:1001
```

脚本内的三要素：

- `KEYS`：脚本要访问的键名数组，由 `EVAL` 的 `numkeys` 参数声明。
- `ARGV`：除键名以外的其他参数。
- `redis.call` / `redis.pcall`：在脚本内执行 Redis 命令。

## 3. 脚本的核心性质

- **原子性**：脚本执行期间服务器被独占，其他客户端的命令排队等待，脚本对外表现为一个原子操作。
- **无隔离级别差异**：由于独占执行，脚本内读到的数据不会被并发修改，无需加锁。
- **错误不回滚**：脚本中途出错时已执行的写命令仍然生效，因此要先校验、后写入。
- **缓存复用**：脚本执行后会被缓存，之后可用 `SCRIPT LOAD` 返回的 SHA1 通过 `EVALSHA` 执行，避免重复传输脚本内容。
- **沙箱受限**：只能使用 Redis 提供的 Lua 库，不能执行文件、网络等系统级操作。

## 4. 与事务（MULTI/EXEC）的取舍

| 需求 | 更适合的机制 |
| --- | --- |
| 顺序执行一批固定命令，不需要中间判断 | `MULTI`/`EXEC` 事务 |
| 需要"读取后根据值决定后续命令"的分支逻辑 | Lua 脚本 |
| 需要在服务器端做计算、聚合、转换 | Lua 脚本 |
| 需要长期维护、随主从同步的脚本集合 | Functions（Redis 7.0+） |

## 5. 使用脚本的注意事项

1. 所有键都放在 `KEYS` 中传入，避免把键名写死在脚本里。
2. 控制脚本执行时间，避免对大集合做全量遍历；超过 `busy-reply-threshold` 后服务器会进入繁忙状态。
3. 生产环境优先使用 `SCRIPT LOAD` + `EVALSHA`（或 `FUNCTION LOAD` + `FCALL`），并在客户端处理 `NOSCRIPT` 错误（重新加载脚本后重试）。
4. 脚本内容一旦修改，SHA1 校验和随之变化，需要重新加载。

## 6. 小结

脚本功能是 Redis 在"单线程原子执行"模型上提供的服务器端编程能力：它用一次往返完成多步逻辑，并天然避免并发竞争。掌握 `EVAL`、`EVALSHA` 与 Functions 的使用方式，是把 Redis 从缓存工具升级为业务引擎的关键一步。
