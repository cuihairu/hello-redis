# The Command Processing Flow

## Overview

A single `GET bd:k` has to travel Redis's entire trunk from byte stream to reply: the event loop picks up events, reads the buffer, parses the protocol, looks up the command table, runs the pre-checks, executes, propagates and updates stats, and finally writes the reply back. Nearly all of this trunk is concentrated in `server.c` (`processCommand()`, `call()`) and `networking.c` (read/write events). This chapter is the overview; the details are developed in the two chapters *Command parsing* and *Command execution*.

## The steps of the full flow

1. **Event ready**: `aeMain()` in `ae.c` -> `aeProcessEvents()` obtains readable events through `aeApiPoll()` (the epoll implementation is in `ae_epoll.c`) and calls back into `readQueryFromClient()`.
2. **Read and parse**: the data lands in `c->querybuf`; `processMultibulkBuffer()`/`processInlineBuffer()` slice out `argv` (each element is a `robj` string object).
3. **Command lookup**: `processCommand()` calls `lookupCommand()` (around line 3306 of `server.c`) to match against the `server.commands` dict. The dict's contents come from `redisCommandTable[]` generated by `commands.def`, where each entry carries the handler function, arity, flags, key specification, and ACL categories.
4. **Pre-checks**: authentication, `CLIENT PAUSE` pause state, memory limit and eviction, arity, read-only replicas rejecting writes, `MULTI` queuing, ACL permissions, script/transaction context, and so on. Any failure returns an error immediately.
5. **Execution**: enter `call()` (around line 3635 of `server.c`), where `c->cmd->proc(c)` does the real work; at the same time this drives statistics, the slow log, latency monitoring, and propagation.
6. **Propagation**: inside `call()`, the command is written to the AOF buffer and `replicationFeedSlaves()` syncs it to the replicas; `alsoPropagate()`/`afterCommand()` handle the extra commands produced while the command executes (such as the DEL triggered by EXPIRE).
7. **Reply**: `addReply*` fills the output buffer; in the `beforeSleep` phase, `handleClientsWithPendingWrites()` writes back to the client.

## What the command table looks like

The command table is referenced in `server.c` as `extern struct redisCommand redisCommandTable[]` (defined in the generated `commands.def`). The `COMMAND` subcommands let you observe the metadata directly:

```bash
$ redis-cli -p 6399 command count
265

$ redis-cli -p 6399 command info get
get
2
readonly
fast
1
1
1
@read
@string
@fast
...
```

The output is, in order: the command name, arity (2 means exactly two arguments), flags, first-key index, last-key index, step, and the ACL categories (`@read @string @fast`). `COMMAND LIST` filters by pattern, and `COMMAND GETKEYS` verifies the key-extraction rules:

```bash
$ redis-cli -p 6399 command getkeys mset bd:a 1 bd:b 2
bd:a
bd:b
$ redis-cli -p 6399 command getkeys eval "return 1" 2 bd:x bd:y
bd:x
bd:y
```

These key specifications are exactly what cluster mode uses to decide "which node this command should be routed to".

## Pre-checks and error feedback

The order of the checks in `processCommand()` determines the order of the common errors: when unauthenticated, only `AUTH`/`HELLO`/`QUIT` and the like are allowed; in an OOM state, write commands are refused (`-OOM command not allowed when used memory > 'maxmemory'`); on a read-only replica, writes are refused (`-READONLY You can't write against a read only replica.`); when a command is not found, an error is reported along with the closest matching command name where possible. In cluster mode, if the slot is not owned by this node, `processCommand()` returns `-MOVED <slot> <ip:port>` and the client completes the redirection.

## Execution and statistics

`call()` uses flags (`CMD_CALL_FULL` and the like) to toggle side effects. The core actions include:

- timing with the `monotonic` clock, written into `usec_per_call` in `INFO commandstats`;
- exceeding `slowlog-log-slower-than` (default 10000 microseconds) sends the entry into the slow log via `slowlogPushEntryIfNeeded()`;
- `latencyAddSample()` records latency events (threshold `latency-monitor-threshold`);
- the `dirty` counter and `replicationFeedSlaves()` propagation;
- `COMMAND COUNT` and `total_commands_processed` in `INFO stats` are incremented here.

The trace of one slow command, observed:

```bash
$ redis-cli -p 16390 debug sleep 0.05        # local instance, enable-debug-command yes
OK
$ redis-cli -p 16390 slowlog get 1
1
1790906194
50093
debug
sleep
0.05
127.0.0.1:40740
```

In order: the entry id, the Unix timestamp, the duration of 50093 (microseconds), the command and its arguments, and the source address. 50093 microseconds exceeds the 10000-microsecond threshold, which is why it was recorded.

## Common commands for observing the whole chain

```bash
redis-cli -p 6399 info stats | grep -E 'total_commands_processed|instantaneous_ops_per_sec'
redis-cli -p 6399 info commandstats | head -8
redis-cli -p 6399 client info          # the last command run on the current connection (cmd= field)
redis-cli -p 6399 slowlog get 3
```

## Summary

The command processing flow is a strictly serial pipeline: event-driven read -> parse -> table lookup -> checks -> `call()` execution -> propagation -> reply. Every "why was this command rejected" or "why wasn't this command written to the AOF" question has its answer on this path through `processCommand()` and `call()`. Once you understand it, you can go on to discuss the "branches off the trunk": multithreaded I/O, blocking commands, and transactions.
